## Purpose

This document collects improvement ideas discovered during manual CSV testing.

Goal:

```text
polish CSV processing first
→ strengthen the internal engine
→ make future Excel/JSON adapters easier
```

# Important Current Limitations

## 01 — Extra Fields Are Ignored Silently

Observed in:

```text
short_extra_rows.csv
```

Current behavior:

```text
extra values beyond known headers are ignored
```

Problem:

```text
silent data loss risk
```

Future improvement:

```text
parse diagnostics for extra fields
```

Example future report:

```json
{
    "parse_diagnostics": {
        "rows_with_extra_fields": [2],
        "extra_field_count": 1
    }
}
```

---

## 02 — Short Rows Are Accepted But Not Explicitly Reported As Parse Issues

Observed in:

```text
short_extra_rows.csv
garbage_lines.csv
```

Current behavior:

```text
missing fields become None
quality report detects missing values
```

Problem:

```text
quality report shows missing values
but does not explain that the source row had too few fields
```

Future improvement:

```text
parse diagnostics for short rows
```

Example:

```json
{
    "parse_diagnostics": {
        "rows_with_missing_fields": [1],
        "missing_field_count": 1
    }
}
```

---

## 03 — Garbage Lines Are Treated As Data

Observed in:

```text
garbage_lines.csv
```

Example:

```csv
THIS IS A RANDOM NOTE LINE
```

Current behavior:

```text
line becomes a short row
first value goes into first column
remaining fields become missing
```

Problem:

```text
random text can pollute data
```

Future improvement:

```text
suspicious row detection
possible comment/garbage line classification
row quarantine candidate
```

Possible rule:

```text
if row has high missing ratio
and first value is long text
and expected first column is numeric
→ possible_garbage_line
```

---

## 05 — Footer / Summary Rows Are Treated As Data

Observed in:

```text
footer_summary_rows.csv
```

Example:

```csv
TOTAL,,650.50,
```

Current behavior:

```text
TOTAL row is treated as normal data
```

Problem:

```text
summary rows can pollute datasets

```

Future improvement:

```text
footer row detection
summary row classification
optional quarantine/remove footer rows
```

Possible rule:

```text
if first column contains TOTAL/SUM/COUNT
and several fields are missing
→ possible_footer_row
```

## 07 — European Decimal Numbers Are Misparsed

Observed in:

```text
european_decimals.csv
```

Expected EU interpretation:

```text
"1.000,50" → 1000.50
"250,75"   → 250.75
"5.500,00" → 5500.00
```

Current incorrect behavior:

```text
"1.000,50" → 1.0005
"250,75"   → 25075.0
"5.500,00" → 5.5
```

Cause:

```text
current number cleaner assumes US-style numbers
comma is treated as thousands separator
```

Future improvement:

```text
locale-aware numeric parsing
```

Needed policies:

```text
US number format: 1,000.50
EU number format: 1.000,50
auto-detect format
column-specific number format
strict parsing mode
```

## 09 — Whitespace-Only Cells Need Verification

Potential issue:

```text
cells containing only spaces or tabs
```

Example:

```csv
customer_id,name,email
1,Alice,"   "
2,Bob,"	"
```

Risk:

```text
null cleaning happens before text cleaning
```

Current pipeline:

```text
null cleaning
→ text cleaning
```

Possible problem:

```text
"   " may become "" after text cleaning
but not converted to None
```

Future improvement:

```text
run null cleaning again after text cleaning
or make text cleaner convert whitespace-only strings to None
or add whitespace-only null handling
```

## 11 — Constraint Integration Still Needed

Constraint engine exists, but pipeline does not yet accept user constraints.

Future goal:

```text
pipeline accepts constraints
→ validates table
→ includes validation report
```

Example constraints:

```python
[
    Constraint("customer_id", "required"),
    Constraint("customer_id", "unique"),
    Constraint("email", "regex_pattern", r"^[^@]+@[^@]+\.[^@]+$")
]
```

# Guiding Principle

Do not move to Excel or JSON until CSV is strong enough.

Reason:

```text
CSV polishing strengthens the shared internal engine.
```

Future formats should only need:

```text
format adapter
→ Table
```

Then they can reuse:

```text
cleaning
type inference
casting
profiling
validation
reporting
export
```
