# Observed Weaknesses and Findings

## 1. Sparse Metadata Rows Initially Broke Header Detection

### Observation

The heavy fixture begins with metadata rows like:

```text
CRM Export: Legacy customer migration;;;;;;;
Generated by: old_crm_v2;;;;;;;
```

These rows contain one meaningful value followed by many delimiter-padding empty fields.

The previous header heuristic selected row `0` as the header because it only checked:

```text
more than one field
matching field count in following rows
```

### Fix Applied

Header detection was updated to ignore sparse metadata rows.

Current behavior:

```text
real header row is selected at index 4
preamble row count is 4
metadata rows are preserved as preamble metadata
```

### Remaining Risk

The heuristic is still heuristic-based.

Future CSV imports may need stronger header scoring based on:

```text
non-empty cell ratio
known header-like words
following row type evidence
field-count stability
user override for header row index
```

## 2. Multiline Notes Are Parsed But Newlines Are Collapsed During Text Cleaning

### Observation

The parser can read a multiline quoted field correctly as one logical cell.

Example source intent:

```text
First line of note
Second line of note
```

After cleaning, the value becomes:

```text
First line of note Second line of note
```

### Interpretation

This is not a parser failure.

It is caused by the text cleaner normalizing internal whitespace.

### Current Expected Behavior

Current tests now expect:

```text
content preserved
embedded newline collapsed to a space
```

### Future Improvement Candidate

Some workflows may need to preserve multiline text exactly.

Possible future option:

```text
preserve_multiline_text = true
```

or profile-based behavior:

```text
light_touch preserves newlines
migration_audit collapses whitespace
```

## 3. Fixture Row Content Can Be Semantically Awkward Because Duplicate Email Columns Shift Expectations

### Observation

The fixture row for whitespace testing contains:

```text
41;Name Whitespace;   Multiple   Internal   Spaces   ;multi@example.com;Germany;...
```

Because the header has duplicate email columns:

```text
Email;Email
```

The value `Multiple   Internal   Spaces` belongs to the primary `email` column, not the `name` column.

### Interpretation

This is a fixture-design sharp edge, not a pipeline bug.

It is useful because it tests duplicate headers and text cleanup at the same time, but test expectations must be precise.

### Current Expected Behavior

The cleaned row should be located by:

```text
name = Name Whitespace
```

and the primary email field should become:

```text
email = Multiple Internal Spaces
```

### Future Improvement Candidate

For readability, a separate row could be added where the `name` column itself contains repeated internal whitespace.

## 4. Diagnostic Report Shapes Differ From Early Test Assumptions

### Observation

```text

```

Actual current shapes are:

```text
type_diagnostics.columns[].column
row_classification.suspicious_rows
```

### Interpretation

This is a test-assumption issue.

### Current Expected Behavior

Tests now use the actual report shape.

### Future Improvement Candidate

Possible future file:


## 5. Accepted Rows Export May Be Header-Only For Very Dirty Fixtures

### Observation

The heavy fixture can produce an accepted rows CSV containing only the header.

This means every parsed row was considered a quarantine candidate under the current constraints/diagnostics.

### Interpretation

This is acceptable for this intentionally dirty fixture.

It means the fixture is heavy enough that no row clearly passes all review gates.

### Current Expected Behavior

Tests should verify:

```text
accepted rows CSV exists
accepted rows CSV has a header
quarantine rows CSV contains representative dirty rows
```

Tests should not require:

```text
Alice Smith appears in accepted rows
```

because constraints and quarantine rules may flag her row due to duplicate email or other global issues.

### Future Improvement Candidate

A separate mixed-quality fixture could include guaranteed-clean rows to test non-empty accepted exports.

Possible future fixture:

```text
tests/fixtures/csv/real_world_mixed_clean_and_dirty_customers.csv
```

## 6. Unbalanced Quote Diagnosis Remains Weak

### Observation

The fixture intentionally contains a broken quote region.

Current parser behavior depends on Python CSV parsing rules and may merge lines or produce irregular rows.

### Current Limitation

The current pipeline may not precisely report:

```text
source line where quote started
source line where quote recovery occurred
whether rows were merged due to malformed quoting
```

### Current Expected Behavior

Do not assert exact malformed quote behavior yet.

Only assert broad structural diagnostics, such as:

```text
extra field diagnostics exist
missing field diagnostics exist
pipeline does not crash if parser can recover
```

### Future Improvement Candidate

Add a malformed CSV pre-scan or parser wrapper that can report quote-balance anomalies.

## 7. Leading-Zero Preservation Is Still A Concern

### Observation

The fixture includes values such as:

```text
00032
00123
01234
```

### Current Risk

If columns are inferred as numeric, leading zeros may be lost.

This is especially risky for:

```text
customer_id
postal_code
phone-like values
```

### Current Expected Behavior

Do not claim leading-zero semantic preservation is solved until verified.

### Future Improvement Candidate

Add semantic text column policies for:

```text
IDs
postal codes
phone numbers
account numbers
```

Possible config/profile option:

```text
force_text_columns = ["customer_id", "postal_code", "phone"]
```

## 8. Currency, Percent, and Text Amounts Need Better Diagnostics

### Observation

The fixture includes amount values such as:

```text
€1.200,50
15%
one hundred
```

### Current Risk

These may be treated as mixed-type values, failed numeric parses, or strings depending dominant type logic.

### Current Expected Behavior

They should not be silently coerced into incorrect numeric values.

### Future Improvement Candidate

Add explicit numeric parse diagnostics for:

```text
currency symbols
percent values
localized thousands/decimal separators
text numbers
```

## 9. Excel Serial Dates Are Likely Unsupported

### Observation

The fixture includes:

```text
45325
```

as an Excel-style serial date example.

### Current Expected Behavior

Do not assume this is a valid date unless date parsing explicitly supports Excel serial dates.

### Future Improvement Candidate

Add optional Excel serial date parsing behind explicit policy.

## 10. German Boolean Tokens May Be Unsupported

### Observation

The fixture includes:

```text
ja
nein
```

### Current Expected Behavior

If unsupported, they should remain visible as mixed/invalid boolean-like values.

### Future Improvement Candidate

Add locale/profile-aware boolean token sets.

Example:

```text
boolean_profile = de
```

## 11. Spreadsheet Injection Hardening Is Not Solved

### Observation

The fixture includes note values like:

```text
=SUM(A1:A2) should stay text
+CMD|' /C calc'!A0
```

### Current Expected Behavior

The pipeline should not execute or reinterpret these values.

### Current Limitation

If exported CSV is opened in spreadsheet software, formula-like text may still be risky.

### Future Improvement Candidate

Add optional export hardening:

```text
escape_formula_like_cells = true
```

Possible risky prefixes:

```text
=
+
-
@
```

---

## 12. HTML-Like Text Is Not Sanitized

### Observation

The fixture includes:

```text
<b>HTML-like note</b>
```

### Current Expected Behavior

The cleaner should preserve it as text.

### Current Limitation

The pipeline should not claim HTML sanitization is implemented.

### Future Improvement Candidate

If HTML reports show raw values in future detailed row previews, ensure values are escaped before rendering.

---

## 13. Extra Fields Are Detected But Not Preserved As Data

### Observation

Rows with extra trailing fields are detected.

Examples:

```text
EXTRA_FIELD
EXTRA1;EXTRA2;EXTRA3
```

### Current Limitation

Extra fields beyond known headers may not be preserved in the normalized table.

### Current Expected Behavior

This is acceptable if parse diagnostics report the issue.

### Future Improvement Candidate

Optional raw-row preservation:

```text
raw_row
extra_fields
source_row_index
```

---

## 14. Summary/Footer Rows Are Flagged But Not Removed

### Observation

Rows like these should appear as suspicious/review candidates:

```text
TOTAL
Grand Total
End of export
Rows exported: 63
```

### Current Expected Behavior

They should not be automatically deleted.

They should remain in normal cleaned output unless explicit quarantine splitting is used.

### Future Improvement Candidate

Add explicit option:

```text
exclude_quarantine_candidates_from_clean_output = true
```

This should be opt-in only.

# Processed Output Policy

The heavy CSV should be run through the pipeline to generate processed outputs during local testing and CI.

Typical output paths:

```text
data/processed/real_world_messy_customers_clean.csv
data/processed/real_world_messy_customers_report.json
data/processed/real_world_messy_customers_report.html
data/processed/real_world_messy_customers_quarantine_candidates.json
data/processed/real_world_messy_customers_quarantine_rows.csv
data/processed/real_world_messy_customers_accepted_rows.csv
```

These files are generated artifacts.

Recommended policy:

```text
do not commit generated processed outputs by default
keep them reproducible through tests, examples, or commands
commit only small expected snapshots if a future stage explicitly needs golden-file testing
```

Reason:

```text
processed outputs can change whenever diagnostics improve
large generated files add repository noise
source fixtures and expected reports are enough for current tests
```
